## 已确认的瓶颈及质量边界

1. **覆盖检查的多次串行往返是主要优化目标。** `coverage_ledger.py` 的 `ITEM_LIMIT=8`。一批缺项可能经过 match、validate_inventory、再次 match、repair、recheck，剩余项还会进入一轮恢复。P9 的 67 个成功模型检查点中，32 个包含 matches，13 个包含 sections（草稿或补漏），其余是清单或其他核对结果。这些分类依据响应字段，不能进一步精确拆分同结构响应的用途。
2. **PR #211 只缩短独立路径，不减少后续核对次数。** 清单并行、清单与草稿重叠能提速，但后续更改同一份正文的补漏/复查仍要保持依赖顺序，不能根据合成样本宣称真实长视频也能快一倍。
3. **成功保存不等于所有质量检查通过。** P5/P8/P9 尚有覆盖未解决项；P10 覆盖清单为 0，但 grounding 仍有未解决段落。已确认这些线上正文保留了 “Completeness is unverified” 提示，没有把未核对状态静默当作质量通过。P7 的完整核对通过。
4. **阶段计时不够细。** 当前所有编辑模型调用聚合为 `model.editor`，无法从历史指标直接分离草稿、清单、匹配、修复、等待并发槽的耗时。实测脚本另记每个模型请求的阶段、开始/结束和状态，便于定位。

建议下一步按实测占比安排：先减少同一草稿的冗余匹配与全稿重复传输；独立匹配只能针对固定版本的草稿并行，合并时必须检测版本变化；补漏与接受修改后的复查保留顺序。不可通过跳过覆盖检查或把 `unverified` 改成通过来提速。

### 建议修改顺序

1. **先改核对和补漏流程。** 评估在固定草稿上批量/并行匹配、合并缺项，再顺序补漏与检查修改影响；避免每 8 项都携带整份草稿反复请求。必须保留依据校验和被撤销的凭据，不能为提速清空未解决项。P9 最后核对撤销大量凭据说明只加速前半段不够。
2. **加入公平调度。** 账号限额保留，但待执行请求按任务轮转或 FIFO，测试首次草稿等待时间及取消清理。当前 semaphore 没有公平性承诺。
3. **整理补漏后的章节。** 按主题和原文顺序组织新增段落，新增“同主题重复章节”检查；合并时保留引用与独立事实，不仅统计完全重复的段落。
4. **补齐观测。** 分开记录排队、等待模型名额、模型各阶段、下载/解码/截图/保存耗时；记录每轮生成会话，避免将最后一轮耗时与累计工作混用。
