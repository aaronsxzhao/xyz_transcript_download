This recording describes a fictional software release incident. The service has a web page, an API, and a background queue. At nine in the morning, release seventeen was deployed. A cached status response continued to show pending for a task that the database had already marked complete. The saved article was present, but the screen did not display it until the next full refresh. The team compared the task identifier, persisted revision, and response revision. The response revision was older than the database revision. This observation supports a cache synchronization problem; it does not prove that the worker failed to save the article. The first corrective action was to invalidate the task cache after a successful save. The second was to reject older status revisions on the page. The team added a regression that saves a completed result, retains an older cache entry, and checks that the next API response contains the completed body. Another regression checks two tabs receiving events in a different order. The first tab should not return to pending after it has seen completion. A later timeout affected a different upstream provider request. That error was classified separately. Retrying it should reuse completed source preparation, but should not reuse an incomplete model response. The release was rolled back in the test environment, then deployed again after the regression checks passed. No production user content was deleted or regenerated during the experiment. The incident report distinguishes local tests, continuous integration, deployment completion, and actual browser acceptance. A successful health endpoint proves availability, not every user workflow. The remaining test is to restart the isolated service while a task is processing, then check the queue lease and the saved result from a fresh browser session.
